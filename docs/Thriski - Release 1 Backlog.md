# Thriski — Release 1 Backlog (Foundations and Single-Lender Onboarding)

*Companion to the Master Requirements and Architecture Document v2.0. Sequences Release 1 (Section 26) into buildable epics, citing the requirement IDs from Section 12 so nothing here needs re-deriving. ID&V provider: Sumsub (OQ-16 resolved).*

## Goal and boundaries

One lender accredits real brokers on the platform, end to end — registration through Active accreditation — with the six non-negotiables (Section 25) built in from the first commit rather than retrofitted. Monitoring, the black/grey lists, the risk indicator, aggregator/association portals, and check reuse across lenders are deliberately out of this release (Section 26); building any of them now is scope creep against the document's own sequencing logic, since Release 2 depends on Release 1's check orchestration existing first.

Every epic below should be built against these constraints regardless of which ticket is in flight: authorisation context required on every read of broker data (no exceptions, no "just for now" bypass); check results, statuses and decisions are append-only with validity intervals, never updated in place; evidence is written once to object storage with an immutability policy and content hash; every domain event lands in the audit log in the same transaction as the change; every billable action emits a metering event even though invoicing itself is out of scope.

## Epic sequence

### 1. Platform foundations
Postgres schema and migrations; the module-boundary skeleton from Section 19 (identity, brokers, businesses, relationships, accreditation, verification, evidence, rulesets, notifications, metering, audit — monitoring and lists scaffolded but empty); the single repository layer requiring an AuthorisationContext on every query (PLT-002, PLT-003); Postgres row-level security policies as the second enforcement layer (Section 20.2); the append-only/temporal table pattern (valid_from/valid_to/superseded_by) established on check_result and carried as the template for every other append-only table; the audit log table, partitioned by month, written in the same transaction as the change it records (AUD-001, AUD-004); the metering_event table and emission hook (BIL-001, BIL-002); cross-tenant access attempts logged and alerted (PLT-005).

*This epic has no user-facing output. It exists so every later epic is built on the right foundation instead of a rewrite in Release 2.*

### 2. Identity, auth and client organisation admin
Broker registration, sign-in, sign-out, password change and reset (AUTH-001–005); MFA on client organisation accounts, mandatory (AUTH-006); client user provisioning, roles and deactivation by a client administrator (AUTH-008); the administrative flow for Thriski operations to create and configure the one lender for Release 1 — entity verification, requirement ruleset assignment, product scopes, branding (W7) — built as an internal tool rather than a polished client-facing feature, since only Thriski operations uses it in Release 1.

### 3. Broker profile build
Personal information capture per Section 13.1, licensing record (ACL held, or CRN and the entity holding the licence), association membership with number and type, experience duration driving the mentoring-letter conditional rule (ONB-003, ONB-005, ONB-006, ONB-012); privacy/terms attestation gating progress (ONB-002); draft save and resume (ONB-008); an outstanding-items view that says exactly what's missing and why (ONB-009) — this is the BRD's most direct "adoption problem, not a revenue one" requirement (Section 1.1), so it earns real design attention rather than a generic checklist.

### 4. Broker business onboarding
The business as a first-class entity, verified independently (BUS-001); a principal can register and complete the business's onboarding (BUS-002); a broker can create a business inline where none exists, or affiliate with an existing verified one — affiliation requires the business's confirmation, not just the broker's assertion (BUS-003–005); one authoritative record per entity shared by every affiliated broker (BUS-006); every principal captured and screened regardless of whether they broker themselves (BUS-007); business-level documents held once, not duplicated per broker (BUS-008); the sole-trader combined journey that derives the business record from the individual's details without asking twice (BUS-013); affiliation history retained with role and dates (BUS-014, BUS-015).

*Sequencing note: this depends on the affiliation/BusinessAffiliation model from the domain model (Section 5.3), not a foreign key on the broker — get this shape right here, since Section 6.5's transfer and business-change handling in later releases assumes it.*

### 5. Documents and evidence store
Object storage with a bucket-level immutability policy, content hashing at capture, metadata and hash pointers in Postgres (Section 20.4) — build this before any document upload ships, since retrofitting immutability after real documents exist means either a migration or an integrity gap. Document upload against required types with outstanding-item tracking (DOC-001); currency and threshold validation, e.g. PI minimum by product scope (DOC-002); document versioning that retains prior versions with their validity periods rather than overwriting (DOC-006); sharing respects relationship scope (DOC-007, not fully exercisable until Epic 9). Data extraction and disparity-highlighting (DOC-003–005) are Should-have — sequence after the Must-have upload path, not before it.

### 6. Identity verification — Sumsub adapter
Build the verification module's provider-adapter interface first (Section 21: submit, poll or callback, normalise, return the raw payload untouched), then implement Sumsub against it for both individual KYC and business KYB — OQ-16's criteria (single provider for both subjects, full payload not pass/fail, Australian document coverage) is exactly what Sumsub was selected against, so the adapter contract should be written generically enough that a second provider (IDV-014, Should-have) is a second adapter, not a rewrite. Broker-triggered ID&V (IDV-001, IDV-002); full result storage with the raw payload as the immutable evidence record and any derived status as a view over it, never a replacement (IDV-003, IDV-009); disparity comparison against broker-entered data (IDV-004); reviewer approve/decline (IDV-005); client-facing full result view — all data, documents, provider assessment, confidence indicators and artefacts, not a pass/fail (IDV-006); provider/method/timestamp visibility (IDV-010); evidence pack export (IDV-011); per-access audit logging (IDV-013).

### 7. Core screening and chain validation
Run the check catalogue (Section 7.1) scoped to what Release 1 needs: business registration and GST status, company status, credit licence and credit representative currency, corporate credit representative status, banned and disqualified, adverse records and directorships, bankruptcy and insolvency (SCR-001). Model every check as a job — requested → in_flight → completed/failed/timed_out (SCR-009) — behind the same adapter pattern as Sumsub, since most of these are separate register/bureau integrations with their own reliability characteristics; where a register has no usable API yet, build the manual-fallback reviewer path from day one (Section 24's "every external source needs a manual fallback" is a Release 1 requirement, not a later nicety). Exception routing to the client's approver with proceed/proceed-with-condition/decline and mandatory rationale (SCR-004, SCR-005). Authority chain validation across licence, corporate credit representative status and individual authorisation as one derived check, not three independent ones (ACR-010) — this is the domain model's central correctness requirement (Section 5.1) and the one most likely to be got wrong if built as three separate boolean checks instead of one chain evaluation.

*Open dependency: which register/bureau providers to integrate for the non-Sumsub checks isn't decided in the master document (OQ-8 touches this for credit/bankruptcy specifically). Worth resolving alongside this epic rather than discovering it mid-sprint.*

### 8. Relationships
Broker selects and links to the lender, with explicit per-relationship consent showing exactly what will be shared before the broker agrees (REL-001, REL-002, Section 2.2); client-initiated invitation and broker accept/decline (REL-003, REL-004); a single view of all relationships and their status (REL-005); revocation with consequences shown (REL-006); consent grants and revocations timestamped, versioned and auditable (REL-010). This epic is also where the **visibility resolution service** (Section 20.2) gets built as a first-class, exhaustively tested component — given (actor, subject, data class), permitted or not — since every subsequent epic's "client can see X" requirement (CLI-*, IDV-006, SCR-010) depends on it existing correctly before it's relied on.

### 9. Ruleset engine
Versioned, declarative JSON configuration per Section 23 — no DSL, no rules-engine product. Required documents with validity windows, conditional rules (experience_years < 2 → mentoring_letter_required), thresholds (PI minimum by product scope), approval routing, training modules and deadlines. Ship with **two seeded rulesets from day one** — one modelled on the Westpac worked example (Annex A), one deliberately different — and treat "the second ruleset needs a code change" as a design defect to fix before this epic is called done, per the document's own test (Section 23).

### 10. Accreditation model and review workbench
The four-party accreditation record (lender, broker, business, aggregator/ACL holder) as its own entity, not a broker-to-lender link (ACR-001, ACR-002); classification (New Broker Introducer, New Referrer Introducer, Transfer, Add-on) driving workflow routing (ACR-004, ACR-005); the credit representative arrangement recorded explicitly, with licence holder modelled as a fillable role rather than assumed to be the aggregator (ACR-008, ACR-009); a party-change flag — pending lender re-acceptance, not suspension — wired up even though the transfer *workflow* itself (Section 6.5) is lighter-weight in Release 1 without a live aggregator portal (ACR-013). The lender review workbench: a filterable work queue (REV-001); profile, documents and check results on one screen (REV-002); request-more-info with itemised reasons (REV-003); approve/decline with mandatory rationale (REV-004); configured approval routing including second-approver or credit sign-off (REV-006); decline notifications to broker and relationship manager (REV-007).

### 11. Training
Training issued on approval (TRN-002); deadline tracking with time-remaining shown to broker and relationship manager (TRN-003, TRN-004); platform vs product training tracked distinctly (TRN-005); completion sets accreditation dates and moves status to Active (TRN-006); missed deadline lapses the accreditation per the client's ruleset (TRN-008) — this is literally the last gate before a broker goes live, so it's worth sequencing right before the workbench epic is considered feature-complete rather than as an afterthought.

### 12. Notifications
Broker notified on submission, information requests, approval, decline, training issue (NOT-001); client users notified on queue entry and check/monitoring return (NOT-002); onboarding pack on activation — code of conduct, identifiers, commission schedule, access details (NOT-003); credentials never sent in plain text (NOT-006); every notification logged against its record (NOT-007).

### 13. Broker profile self-service and audit surfacing
As a small but important closing epic: the broker's own profile view (progress, outstanding tasks, notifications, information updateable at any time, visibility of who it's shared with) (PRF-001–006); the broker-facing access history — which organisations viewed what, and when (AUD-003); the point-in-time reconstruction capability exercised end-to-end for the first time (AUD-005), since everything upstream was built to support it but this is where it's actually proven against real data.

## Explicitly not in this backlog

Monitoring (Release 2, all of MON-*), the black and grey lists and lender-private concerns (Release 3/4, BLK-*/GRY-*/LRC-*/PLA-*), the conduct risk indicator (Release 4, RSK-*, though RSK-017's outcome-data capture is worth wiring into events now per the non-negotiables), aggregator and association portals, check reuse across lenders, and in-solution chat (Could-have regardless of release). Building any of these into Release 1 delays the thing that actually proves the product: one lender accrediting real brokers end to end.

## Before Sprint 1 actually starts

Two things outside this backlog's control still block a clean start: which register/bureau providers cover the non-Sumsub checks in Epic 7 (business registration, licence/CRN currency, banned-and-disqualified, adverse records, bankruptcy), and confirmation of team size/timeline/stack, which the master document flags as unconfirmed (Section 28). Neither blocks *starting* — Epic 1 and most of Epic 2 don't depend on either — but Epic 7 will stall without a provider decision, so it's worth resolving in parallel with Epics 1–4 rather than after them.
