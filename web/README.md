# Thriski — web

Frontend foundations: Next.js 16 (App Router) + Tailwind v4 + hand-built shadcn-style
components (Button, Input, Card, Table, etc. — see "Why hand-built, not the shadcn
CLI" below). Proves the design system and two representative screens; the rest of the
UI gets built on top of this.

## What's here

- `src/app/globals.css` — every design token (colour, status meaning, font stack).
  Read this before adding a colour anywhere else in the app.
- `src/lib/status.ts` — maps every backend status enum value to one of five semantic
  meanings (success/warning/danger/info/neutral). This is the file to edit when a new
  status value is added to the backend schema.
- `src/components/status-badge.tsx` — the ONLY component allowed to render a status
  colour. Every screen uses this rather than reinventing a badge.
- `src/lib/api-client.ts` — the seam between screens and data. Currently backed by
  `src/lib/mock-data.ts`; swap for real `fetch()` calls once Epic 2's HTTP API exists.
  Screens import from here, never from mock-data.ts directly.
- `/design-system` route — every token and status badge rendered on one page. Open
  this first when working on any screen, and add to it when a new component pattern
  is introduced.
- `/register` — the broker onboarding form (ONB-001–012 subset): validation, draft
  save that deliberately bypasses validation, and a persistent stepper showing the
  whole onboarding journey even for steps not built yet.
- `/reviewer/queue` and `/reviewer/brokers/[id]` — the lender review workbench
  (REV-001/002): filterable dense table, and a detail view with an evidence
  disclosure pattern (Section 2.4 — full evidence, not a pass/fail badge, one click
  away).

## Why hand-built components, not the shadcn CLI

`npx shadcn@latest init` needs `ui.shadcn.com`, which wasn't reachable in the sandbox
this was built in (npm's registry was). The components here follow the same patterns
(Tailwind + `class-variance-authority`, accessible-by-default HTML) by hand instead.
If `ui.shadcn.com` is reachable in your environment, running the CLI against this
project should be safe — it writes to `src/components/ui/*`, the same location these
hand-built ones live, so review the diff rather than assuming a clean merge.

## Running

```bash
npm install
npm run dev     # http://localhost:3001 — 3000 is reserved for the backend API, see below
npm run build   # production build — verified clean, zero warnings, as of this scaffold
npm run lint
```

The dev server runs on **3001**, not Next's default 3000, because the backend's `PORT`
(`.env` / `src/config/env.ts`) also defaults to 3000 and the two run side by side in
local dev. If you change one, change the other's expectation too — nothing enforces
this pairing automatically.

If you run `tsc --noEmit` standalone (e.g. in a CI step separate from `next build`) on
a fresh checkout, it will fail on `layout.tsx`'s `LayoutProps<"/">` with "Cannot find
name" — that type is generated by Next itself (`.next/types/**/*.ts`, included via
tsconfig) and doesn't exist until something has run `next dev`, `next build`, or
`npx next typegen` at least once. This is Next 16 behaviour, not a bug in this repo;
run `npx next typegen` first if you want a standalone type-check step in CI.

No backend connection is required yet — every screen reads from typed mock data
(`src/lib/mock-data.ts`) via `src/lib/api-client.ts`. See that file's top comment for
what changes once Epic 2's HTTP layer exists on the backend.

## Fonts

Deliberately NOT `next/font/google` — see the comment at the top of
`src/app/layout.tsx`. `fonts.googleapis.com` wasn't reachable when this was built,
and depending on it means the production build can fail in any similarly locked-down
network. The system-font stack in `globals.css`'s `--font-sans` is the fix; swap in a
licensed, self-hosted font via `next/font/local` if the product needs a distinct type
identity later.

## Next steps

Everything past these three screens is a straightforward extension of the same
patterns: document upload (Epic 5) is another form using `Field`/`Input`; the client
dashboard (Epic 12) is another filtered table like the reviewer queue; business
onboarding (Epic 4) is another multi-field form like registration. The design system
page is the check — if a new screen needs a colour, component shape, or status
treatment that page doesn't already show, add it there first, then use it.
